### Frontend — Angular

**Essência do que o enunciado exige no frontend**
O NzolaNet é uma rede social web onde o utilizador cria conta, recupera senha, edita perfil, altera foto, segue/deixa de seguir outros utilizadores, publica conteúdo com texto e multimédia, reage com bazes, comenta, vê feed cronológico e recebe notificações. O sistema também exige interface responsiva, usabilidade intuitiva, compatibilidade móvel, segurança na autenticação e proteção contra acessos não autorizados. 

**Leitura prática para o frontend**
O frontend não deve inventar redesenhos ou funcionalidades fora do enunciado. O que precisa existir é uma aplicação Angular modular, com componentes reutilizáveis, separação entre páginas, componentes de UI e serviços, e experiência fluida para feed, perfil, criação/edição de publicações, comentários, bazes e notificações. A visualização de vídeos e imagens publicados também é obrigatória.

**Estrutura recomendada de pastas no Angular**
`src/app/core` para serviços globais, guardas, interceptors e autenticação;
`src/app/shared` para componentes reutilizáveis, pipes, directives e modelos comuns;
`src/app/features/auth` para login, registo e recuperação de senha;
`src/app/features/profile` para perfil, edição, foto e privacidade;
`src/app/features/posts` para feed, detalhe da publicação, criação, edição, remoção e upload de mídia;
`src/app/features/interactions` para bazes e comentários;
`src/app/features/notifications` para listar notificações;
`src/app/features/users` para seguir/deixar de seguir e visualização de perfis;
`src/assets` para imagens estáticas e ícones;
`src/environments` para endpoints por ambiente.
Esta organização é a forma mais limpa de cumprir a exigência de separação entre interface, lógica e serviços, mantendo reutilização real de código. 

**Componentes reutilizáveis que devem existir**
`app-navbar`, `app-sidebar`, `app-user-avatar`, `app-post-card`, `app-post-media`, `app-like-button`, `app-comment-item`, `app-comment-form`, `app-notification-item`, `app-loading`, `app-empty-state`, `app-confirm-dialog`, `app-error-banner`.
Isto evita duplicação e ajuda a manter consistência visual em toda a aplicação. Como o enunciado pede usabilidade intuitiva e responsiva, estes componentes devem ser pequenos, focados e combináveis. 

**Módulos/páginas principais**
`AuthModule`: login, registo, recuperação de senha;
`FeedModule`: feed principal, feed de utilizadores seguidos, ordenação cronológica e atualização dinâmica;
`PostsModule`: criar, editar, apagar, carregar imagem/vídeo, ver publicação;
`CommentsModule`: adicionar, editar, apagar e listar comentários;
`UsersModule`: perfis, seguir/deixar de seguir, privacidade;
`NotificationsModule`: listagem e estado de leitura;
`AdminModule` se o grupo quiser isolar a moderação de comentários ofensivos, que o enunciado permite ao administrador remover.

**Fluxo de ecrãs mínimo para nota alta**
Login → Registo → Recuperação de senha → Feed → Perfil próprio → Perfil de outro utilizador → Detalhe da publicação → Modal/linha de comentários → Notificações → Ecrã de edição de publicação/perfil.
O feed deve mostrar conteúdo recente e conteúdo de utilizadores seguidos, em ordem cronológica, com atualização dinâmica, porque isso está explicitamente pedido.

**DTOs no frontend**
Deve haver modelos TypeScript separados por caso de uso, por exemplo: `UserDto`, `UserProfileDto`, `PostListItemDto`, `PostDetailDto`, `CommentDto`, `NotificationDto`, `CreatePostRequestDto`, `UpdatePostRequestDto`, `FollowActionDto`, `AuthResponseDto`.
Isso evita acoplamento direto ao contrato interno do backend e casa com a exigência de usar DTOs em ambos os sentidos. 

**Regras de interface que não devem ser quebradas**
A UI deve impedir ações inválidas antes mesmo de chamar a API: editar/apagar apenas conteúdos próprios, impedir base duplicada do mesmo utilizador na mesma publicação, esconder ações não autorizadas, e refletir privacidade do perfil conforme as regras do backend. O enunciado diz explicitamente que apenas utilizadores autenticados podem publicar e que cada utilizador só pode editar ou excluir conteúdos da sua autoria.

**Tecnologias recomendadas no frontend**
Angular, TypeScript, RxJS, Angular Router, Reactive Forms, HttpClient, Angular Material ou outra biblioteca de UI consistente, e eventualmente Tailwind se a equipa dominar bem e quiser velocidade visual. O importante é manter responsividade, consistência e boa navegabilidade, porque isso é parte dos requisitos não funcionais. 

**[bloqueado] pontos que o PDF não especifica**
Não há no enunciado a definição exata de layout, paleta, branding, número de páginas obrigatórias, regras detalhadas de moderação, nem o comportamento exato da privacidade “privado” além de “acessível apenas a utilizadores autorizados”. Nesses pontos, a implementação deve ser feita com a opção mais conservadora e reversível, sem inventar regras novas.

### Backend — ASP.NET Web API + SQL Server

**Essência do que o enunciado exige no backend**
O backend tem de suportar gestão de utilizadores, publicações, bazes, comentários, feed de notícias e notificações. Além disso, deve garantir que só utilizadores autenticados publicam, que cada pessoa só altera o que é seu, que não há bazes duplicados na mesma publicação e que comentários ofensivos podem ser removidos pelo administrador.

**Stack final coerente para o teu grupo**
Como tu já escolheste ASP.NET Web API e SQL Server, essa deve ser a base oficial do projeto. O PDF lista também PHP/Laravel e MySQL/PostgreSQL como opções técnicas, mas como o enunciado não obriga a usar todas, o melhor é fixar uma única stack para evitar fragmentação e incompatibilidades. 

**Arquitetura recomendada por camadas**
`NzolaNet.Api`
`NzolaNet.Application`
`NzolaNet.Domain`
`NzolaNet.Infrastructure`
`NzolaNet.Shared`

No sentido prático:
`Api` recebe requests e devolve responses;
`Application` contém regras de negócio, casos de uso e DTOs;
`Domain` guarda entidades e regras centrais;
`Infrastructure` trata de SQL Server, Entity Framework Core, repositórios e integrações;
`Shared` pode conter resultados genéricos, enums, constantes e helpers.

Esta abordagem cumpre diretamente a exigência de separação por camadas. 

**Estrutura de pastas recomendada no backend**
`Controllers/`
`Dtos/Requests/`
`Dtos/Responses/`
`Services/Interfaces/`
`Services/Implementations/`
`Repositories/Interfaces/`
`Repositories/Implementations/`
`Domain/Entities/`
`Domain/Enums/`
`Domain/Specifications/` se necessário
`Infrastructure/Data/`
`Infrastructure/Migrations/`
`Infrastructure/Configurations/`
`Infrastructure/Seed/`
`Application/Validators/`
`Application/Mappings/`
`Application/Exceptions/`
`Application/Contracts/`

Assim, Controllers ficam finos, Services concentram a lógica, Repositories só tratam persistência, e DTOs isolam o contrato externo. 

**Entidades mínimas da base de dados**
`Users`
`UserProfiles`
`Posts`
`PostMedia`
`PostLikes` ou `PostBazes`
`Comments`
`Follows`
`Notifications`
`PasswordResetTokens`
`Roles` se quiseres formalizar Admin/Utilizador
`UserPrivacySettings` se preferires separar a privacidade do perfil

Isto cobre tudo o que o enunciado pede: utilizadores, publicações, bazes, comentários, feed e notificações.

**Modelo relacional recomendado**
`Users (1) -> (1) UserProfiles`
`Users (1) -> (N) Posts`
`Users (1) -> (N) Comments`
`Users (1) -> (N) Notifications`
`Users (N) <-> (N) Users` via `Follows`
`Users (N) <-> (N) Posts` via `PostLikes`/`Bazes`
`Posts (1) -> (N) Comments`
`Posts (1) -> (N) PostMedia`

A tabela de bazes deve ter uma restrição única em `(PostId, UserId)` para impedir múltiplos bazes do mesmo utilizador na mesma publicação, como o enunciado exige. 

**Normalização sugerida**
A base deve seguir no mínimo 3FN:
dados de autenticação em `Users`;
dados de apresentação em `UserProfiles`;
relacionamentos N:N em tabelas de junção;
multimédia separada de `Posts`;
notificações separadas de qualquer entidade principal.
Isto evita repetição, facilita manutenção e mantém o sistema consistente. O enunciado dá prioridade à integridade e organização das informações. 

**Campos principais por tabela**
`Users`: Id, Username, Email, PasswordHash, RoleId, IsActive, CreatedAt
`UserProfiles`: Id, UserId, FullName, Bio, ProfilePhotoUrl, PrivacyType, UpdatedAt
`Posts`: Id, AuthorId, Text, CreatedAt, UpdatedAt, IsDeleted
`PostMedia`: Id, PostId, MediaType, FileUrl, ThumbnailUrl, OrderIndex
`PostLikes`: Id, PostId, UserId, CreatedAt
`Comments`: Id, PostId, AuthorId, Content, CreatedAt, UpdatedAt, IsDeleted
`Follows`: Id, FollowerId, FollowedId, CreatedAt, Status
`Notifications`: Id, UserId, Type, Message, IsRead, CreatedAt, RelatedEntityId, RelatedEntityType
`PasswordResetTokens`: Id, UserId, TokenHash, ExpiryDate, UsedAt

Os campos acima são uma proposta técnica coerente com os requisitos, sem contrariar o PDF. Os nomes exatos podem mudar, mas a estrutura funcional deve manter-se.

**Regras de negócio que o backend deve impor**
Só utilizador autenticado cria publicação;
só autor edita/apaga a sua publicação;
só autor edita/apaga o seu comentário;
um utilizador só pode dar baze uma vez por publicação;
remover baze é permitido apenas para quem deu a baze;
comentários ofensivos podem ser removidos pelo administrador;
perfil público é visível a todos os membros da plataforma;
perfil privado só é visível para utilizadores autorizados;
novo baze gera notificação;
novo comentário gera notificação;
novo seguidor gera notificação.

**[bloqueado] ponto ambíguo da privacidade**
O enunciado diz “utilizadores autorizados”, mas não define o mecanismo de autorização do perfil privado. A implementação mais segura é assumir acesso só para o próprio utilizador e, se o professor aceitar, para seguidores aprovados manualmente. Como isso não está especificado, o ideal é documentar a regra escolhida no relatório.

**Estratégia de autenticação e segurança**
Como o enunciado insiste em autenticação segura e proteção contra acessos não autorizados, o backend deve usar autenticação com token, hashes fortes de palavra-passe e autorização por papéis. O papel `Admin` é necessário para a moderação de comentários, porque o PDF atribui essa capacidade ao administrador. 

**Feed de notícias**
O feed deve devolver publicações recentes e de utilizadores seguidos, em ordem cronológica, com atualização dinâmica. Tecnicamente, isso pede uma query própria de feed, paginação, ordenação por `CreatedAt DESC`, e um endpoint que o frontend possa chamar periodicamente ou via atualização assíncrona. 

**Upload de imagens e vídeos**
O backend deve validar tipo, tamanho e integridade do ficheiro, guardar metadados em `PostMedia` e devolver URLs utilizáveis pelo frontend. O enunciado exige upload de imagens e vídeos e visualização de conteúdo multimédia publicado. 

**Estratégia de Git e GitHub para 4 pessoas**
A melhor solução é um repositório único com duas raízes: `/frontend` e `/backend`. Isso facilita integração final e evita “dois projetos soltos” no fim. Usa `main` como branch protegida e `develop` como branch de integração. Cada tarefa deve nascer em branch própria: `feature/frontend-feed`, `feature/backend-posts`, `feature/backend-auth`, `feature/frontend-profile`, etc.
Toda entrega entra por Pull Request com review de pelo menos uma pessoa. Ninguém faz push direto para `main`. O merge para `develop` pode ser por merge commit ou squash, mas eu recomendo `squash` para features pequenas e `merge commit` para módulos grandes, porque facilita rastreio.
Antes de fechar PR: pull da `develop`, resolver conflitos localmente, executar testes e confirmar que o contrato DTO/API não foi quebrado.
No fim de cada marco, `develop` é promovida para `main` com tag de versão.

**Divisão de trabalho prática entre frontend e backend**
Os 3 do frontend devem trabalhar por módulos: autenticação, feed/perfil, interações/notifications. Tu, no backend, ficas com entidades, base de dados, API, regras de negócio, autenticação e documentação técnica.
A regra de ouro é esta: qualquer alteração que mexa no contrato entre frontend e backend deve passar por um ficheiro partilhado de especificação, nem que seja um documento interno com endpoints, requests e responses. Isso reduz conflitos e retrabalho.

**Plano que maximiza a nota**
Entregar cedo a base funcional: autenticação, utilizadores, publicações, comentários.
Depois bazes, seguidores, feed e notificações.
Por fim polimento visual, responsividade, validações, moderação de comentários e relatório final.
O próprio enunciado separa a entrega intermédia em gestão de utilizadores, publicações e comentários, e a entrega final em aplicação completa + relatório. 

**Conclusão técnica**
O que vai dar força ao projeto não é inventar funcionalidades, mas cumprir bem o núcleo pedido: rede social simples, segura, consistente, organizada em camadas, com DTOs, feed cronológico, interações sem duplicação, notificações e boa UX. Essa é a leitura mais fiel do PDF e a mais segura para um 20/20.
