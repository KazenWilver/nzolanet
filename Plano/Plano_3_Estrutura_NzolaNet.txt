### 1. Análise Profunda e Essência do Projeto NzolaNet

A NzolaNet é uma Aplicação Web de rede social projetada para facilitar a comunicação, partilha de informações e interações digitais. O ecossistema baseia-se em cinco pilares funcionais: Utilizadores, Publicações, Bazes (reações), Comentários e Notificações.

**Regras de Negócio e Restrições Críticas (Extraídas do Enunciado):**

* 
**Segurança e Autoria:** Apenas utilizadores autenticados podem publicar. Edição e exclusão de publicações ou comentários são estritamente restritas aos respetivos autores.


* 
**Integridade de Interação:** O sistema deve bloquear múltiplos "bazes" do mesmo utilizador numa mesma publicação.


* 
**Moderação:** Existe a figura do Administrador do sistema, com privilégios para remover comentários ofensivos ou que violem políticas.


* 
**Privacidade:** O perfil do utilizador tem estados mutuamente exclusivos: Público (visível a todos) ou Privado (visível apenas a autorizados/seguidores).


* 
**Composição da Publicação:** A abstração visual de uma publicação exige a compilação de dados relacionais (nome e foto do autor, contagem de bazes e comentários) juntamente com os dados intrínsecos (texto, multimédia, data).



**Identificação de Ambiguidades/Lacunas (Para evitar adivinhações):**

* 
*Recuperação de Senha:* O enunciado pede "Recuperação da senha"  mas não especifica o método (E-mail com token, perguntas de segurança). *Pressuposto técnico adotado:* Envio de Token OTP/Link via E-mail (padrão da indústria).


* 
*Gestão de Administradores:* Menciona remoção de comentários pelo administrador, mas não especifica como o administrador é criado. *Pressuposto técnico adotado:* Implementação de um sistema de `Roles` (Utilizador comum / Administrador) na base de dados, com um administrador semeado (*seeded*) via código.

### ARQUITETURA FRONTEND (ANGULAR)

**Equipa:** 3 Elementos


**Objetivo:** Interface responsiva, usabilidade intuitiva, compatibilidade mobile e consumo eficiente via DTOs.

**Tecnologias e Bibliotecas Recomendadas:**

* **Framework:** Angular (versão LTS mais recente).
* **Estilização:** Tailwind CSS (garante responsividade e compatibilidade mobile rápida) ou Bootstrap.
* **Gestão de Estado:** RxJS (BehaviorSubjects em Services para partilha de dados entre componentes) ou Signals (Angular 16+).
* **Interceções:** HttpInterceptor para injetar automaticamente o Token JWT em cada requisição e tratar erros globais (ex: 401 Unauthorized).

**Organização de Diretórios (Arquitetura Modular):**
A melhor abordagem para 3 pessoas trabalharem em simultâneo no Angular é dividir a aplicação em módulos por domínio (*Feature Modules*).

```text
/src
  /app
    /core           # Serviços singletons (AuthService, TokenService), Interceptors, Guards.
    /shared         # Componentes reutilizáveis (PostCardComponent, NavbarComponent), Pipes, Diretivas.
    /features       # Módulos independentes (cada membro pode focar-se num módulo sem gerar conflitos).
      /auth         # Componentes: Login, Registo, Recuperação de Senha.
      /feed         # Componentes: Feed Principal, Feed de Seguidos.
      /profile      # Componentes: Ver Perfil, Editar Perfil.
      /posts        # Componentes: Criar Publicação, Detalhes da Publicação.
      /notifications# Componentes: Lista de notificações dropdown/página.
    /models         # Interfaces TypeScript mapeadas EXATAMENTE para os DTOs do Backend.

```

**Estratégia de Execução no Frontend:**

1. **Componentização Inteligente:** Criar um `PostComponent` que recebe um `PostDTO` como `@Input()`. Este componente lidará com as funções de dar Baze e Comentar. Desta forma, é reutilizado no `Feed` e no `Perfil`.


2. 
**Guards de Rota:** Implementar `AuthGuard` para garantir proteção contra acessos não autorizados nas rotas `/feed` e `/profile`.


3. 
**Upload de Multimédia:** Utilizar `FormData` no serviço Angular para enviar ficheiros (fotos e vídeos) para o backend.

### ARQUITETURA BACKEND (ASP.NET WEB API & SQL SERVER)

**Equipa:** 1 Elemento (Willfredy)


**Objetivo:** Separação de camadas rigorosa, segurança, performance e normalização da base de dados.

**Tecnologias Recomendadas:**

* **Framework:** ASP.NET Core Web API (.NET 8).
* **ORM:** Entity Framework Core (EF Core) com abordagem Code-First.
* 
**Base de Dados:** SQL Server.


* **Autenticação:** JWT (JSON Web Tokens) com ASP.NET Core Identity.
* **Mapeamento de DTOs:** AutoMapper.

Organização de Pastas (Separação por Camadas ):
Vais criar uma solução (`.sln`) estruturada em múltiplos projetos (Class Libraries) para garantir o isolamento perfeito:

```text
NzolaNet.Solution/
│
├── NzolaNet.API (Camada de Apresentação)
│   ├── Controllers/ (ex: AuthController, PostsController, UsersController)
│   ├── Program.cs (Injeção de dependências, CORS, JWT Setup)
│
├── NzolaNet.Application (Camada de Serviços / Lógica de Negócio)
│   ├── Services/ (Implementação das regras de negócio, ex: IPostService, PostService)
[cite_start]│   ├── DTOs/ (Input e Output para comunicação com a API [cite: 94])
│   ├── Mappings/ (Perfis do AutoMapper)
│
├── NzolaNet.Domain (Camada de Domínio)
│   ├── Entities/ (Modelos da Base de Dados: User, Post, Comment, Baze, Notification)
│   ├── Interfaces/ (Contratos para os Repositórios)
│
└── NzolaNet.Infrastructure (Camada de Acesso a Dados)
    ├── Data/ (ApplicationDbContext, EF Migrations)
    ├── Repositories/ (Implementação concreta das interfaces, EF Core queries)

```

**Base de Dados SQL Server - Esquema e Normalização (Entidades Principais):**
Para obter "Boa performance no carregamento", as tabelas devem estar normalizadas (3NF) e devidamente indexadas.

* `Users`: Id (PK), Username, Email, PasswordHash, ProfilePhotoPath, IsPrivate (bool), Role (User/Admin).
* `Followers`: FollowerId (FK para Users), FollowedId (FK para Users). *PK Composta (FollowerId, FollowedId).*
* `Posts`: Id (PK), UserId (FK), Text, ImagePath, VideoPath, CreatedAt.
* `Comments`: Id (PK), PostId (FK), UserId (FK), Text, CreatedAt.
* `Bazes`: PostId (FK), UserId (FK). *PK Composta (PostId, UserId)* - Isto satisfaz diretamente o requisito de impedir múltiplos bazes.


* `Notifications`: Id (PK), UserId (FK), Type (Baze/Comment/Follow), TriggeredByUserId (FK), IsRead (bool), CreatedAt.

**Estratégia de Performance (Crucial para o 20/20):**

* 
**DTOs Otimizados:** O frontend exige que a publicação venha com nome do autor, foto, e números de bazes/comentários. Não devolvas a entidade `Post` inteira. Usa o EF Core para projetar (.Select) diretamente num `PostResponseDTO` contendo `BazesCount = p.Bazes.Count()` para não carregar dados desnecessários na memória.


* 
**Paginação:** No `Feed de Notícias`, implementa paginação nos repositórios (`Skip` e `Take`) para garantir a atualização dinâmica e carregamento leve.

### ESTRATÉGIA DE COLABORAÇÃO (GIT & GITHUB)

Para trabalharem de forma harmoniosa, sem destruírem o código uns dos outros e garantindo uma entrega limpa até às datas estipuladas (Segunda Parcelar e Exame ), sigam esta metodologia profissional:

**1. Estrutura do Repositório:**
Aconselho **um único repositório (Monorepo)** com duas pastas na raiz: `/frontend-angular` e `/backend-dotnet`. Assim, o professor avalia o projeto inteiro num só lugar.

**2. Sistema de Ramificação (Branching Strategy - GitHub Flow modificado):**

* `main`: O código intocável, sempre a funcionar. Reflete o que vai ser entregue.
* `develop`: A branch de integração. Tudo junta-se aqui primeiro.
* **Branches de Funcionalidade:** NUNCA codifiquem diretamente na `develop` ou `main`.
* Willfredy (Backend): Cria branches como `backend/feat-auth`, `backend/feat-post-endpoints`.
* Equipa Frontend: Cria branches como `frontend/feat-feed`, `frontend/ui-profile`.



**3. Evitar Conflitos (Para os 3 de Frontend):**
Sendo 3 pessoas a mexer no Angular, os conflitos de *merge* ocorrem no `app.module.ts` ou nas rotas. A arquitetura de Módulos (sugerida acima) previne isto. Se o João está a trabalhar no módulo `/auth` e a Maria no `/feed`, eles mexem em ficheiros diferentes. Quando fizerem merge na `develop`, os conflitos serão mínimos.

**4. Fluxo de Trabalho Diário (Pull Requests):**

1. Faz `git pull origin develop` para ter o código mais atual.
2. Cria a branch: `git checkout -b frontend/feat-comentarios`.
3. Faz commits pequenos e com significado estruturado: `feat(comments): adicao do DTO e layout de comentarios`.
4. Envia para o GitHub: `git push origin frontend/feat-comentarios`.
5. Abre um **Pull Request (PR)** da tua branch para a `develop`.
6. Um colega **DEVE** rever o código antes de aceitar (Code Review). Isto prova maturidade de engenharia no vosso relatório.
